# Создание интерактивного примера для темы

Пример — файл `data/examples/<id темы>.gms`, который компилируется
`assets/js/gms-compiler.js` в HTML и показывается на странице темы справочника.
Требования к готовому примеру — в [standard.md](standard.md). Это живой документ:
каждое замечание пользователя, которое касается не только текущего примера, сразу
записывается туда (или в этот файл, если оно про процесс), в том же коммите, что и
исправление.

## 1. Тема и её описание

1. Найти тему в `data/topics/config.json` (плоский массив, поля `id`, `title`,
   `parent`, `description`, `keywords`, `example`):
   ```bash
   node -e 'const c=require("./data/topics/config.json");for(const t of c.filter(t=>/Параллелограмм/.test(t.title)))console.log(t.id,"|",t.title,"|",t.type,"|",t.example||"")'
   ```
   Одна тема может встречаться несколько раз («… (см. Раздел → Подраздел)» —
   ссылки-дубликаты). Пример делается для основной темы.
2. **Прочитать описание темы целиком** и сделать пример в гармонии с ним: те же
   обозначения (буквы точек, имена величин), те же формулировки определений и
   свойств, тот же порядок изложения. Пример не должен вводить понятий, которых нет в
   описании, и противоречить ему.
3. Если описания нет (или оно пустое / заглушка) — написать его и сохранить в
   `description` темы. Формат как у соседних тем: HTML-абзацы `<p>…</p>`, ссылки на
   другие темы — `<a href="topic:<id>">…</a>`, формулы — `$…$`. Сначала определение,
   затем свойства — ровно те, что показывает пример.
4. Если пример естественно показывает то, чего в описании нет, а в описании это к
   месту, — дополнить описание, а не обеднять пример.

`config.json` весит ~8 МБ: править его точечно (вставкой строк), а не
перезаписью через `JSON.stringify`, чтобы в диффе были только нужные строки.

## 2. Проектирование

До написания кода ответить себе:
- **Что двигает пользователь** и какое ограничение сохраняет объект темы (п. 3 и 5
  стандарта): «параллелограмм остаётся параллелограммом», «точка на графике» и т. д.
- **Вкладки**: какие свойства из описания темы показывает каждая (п. 6).
- **Что попадает в описание под полем** для каждой вкладки (п. 7).
- **Поле**: `field width` / `field height` под размер объекта, `camera type = fixed;`
  (п. 8).

## 3. Язык GMS — проверенные на практике детали

`data/gms-docs/core-2d.md` местами расходится с компилятором. Верить парсеру
(`parse*Block` в `assets/js/gms-compiler.js`), а не справочнику. Проверено:
- `new Angle { name; lines = (l1, l2) }` + отдельный `draw Angle { angle = "имя"; count }`.
- `draw Punctir` / `draw Vector` — поле `edge = "линия"`.
- Действие кнопки — строка в кавычках: `action = "tab = 2; t1.active = false"`.
- Точка на объекте: `line = "имя"` (в кавычках), `t` — параметр 0…1; `graph = "имя"`.
- В выражениях объекты доступны по имени: `A.pos.x`, `ab.length`, `angA.measure`,
  `X.t` у точки на прямой; присваивание `A.pos.x = …` в `Update` двигает точку.
- `Function f(a, b) { float x = …; if (…) { return …; } return …; }` — локальные
  переменные, `repeat (n) { … i … }`, `max(…)`, `format(x, 2)`, `round`, `abs`.
- `fieldMaxX` / `fieldMaxY` — граница поля для центров точек (с отступом в радиус).
- Живое описание: `description = "{info}"`, строка `info` собирается в `Update`;
  внутри работают `**жирный**` и `\n\n` между абзацами.

Если язык чего-то не умеет или ведёт себя неправильно — это баг компилятора: чинить
в `gms-compiler.js` (с комментарием «почему», как принято в файле), а не обходить в
примере. После любой правки компилятора перекомпилировать и проверить **все**
примеры из `data/examples/` (шаг 4).

## 4. Тестирование

Все временные файлы — в scratchpad, не в репозитории.

1. **Компиляция** (ноль ошибок):
   ```bash
   node .claude/skills/gms-example/scripts/compile.mjs data/examples/<id>.gms <scratch>/<id>.html
   ```
2. **Консоль и внешний вид** — каждая вкладка в обеих темах:
   ```bash
   node .claude/skills/gms-example/scripts/check.mjs <scratch>/<id>.html <scratch>/chk "Вкладка 1" "Вкладка 2"
   ```
   Выход 1 — в консоли были предупреждения/ошибки. Скриншоты (`dark-N.png`,
   `light-N.png`) **посмотреть глазами**: масштаб, контраст в обеих темах, подписи не
   обрезаны и не налезают, текст описания верный.
3. **Взаимодействие** — отдельный Playwright-скрипт в scratchpad (образец — в
   `check.mjs`: импорт Playwright через `npm root -g`, браузер
   `/opt/pw-browsers/chromium-1194/chrome-linux/chrome`). Координаты холста брать
   заново после каждого клика по вкладке: длина описания меняется, и холст
   сдвигается. Проверить:
   - каждую перетаскиваемую точку и фигуру целиком — объект меняется как задумано;
   - «злые» ходы: за край поля, в угол, через другую точку, в вырожденное положение,
     резкий рывок мышью, затем попытка схватить точку у края снова;
   - **фаззинг**: 50+ случайных резких ходов (точки и фигура целиком) с проверкой
     инварианта темы после каждого (для параллелограмма `A + C = B + D`, все точки
     внутри `fieldMaxX/fieldMaxY`). Несколько разных seed'ов.
4. **Регрессия**: скомпилировать все `data/examples/*.gms` — ни одной ошибки.

## 5. Привязка к теме и пуш

1. В записи темы в `config.json` поле `"example": "data/examples/<id>.gms"` (как
   делает кнопка «Создать пример» в справочнике).
2. Коммит в **main**, без побочных веток: `git add` конкретных файлов, сообщение на
   русском — что сделано в примере и отдельным блоком что исправлено в компиляторе.
   ```bash
   git push origin main
   ```
3. Пользователю — через SendUserFile исходный `.gms` и скомпилированный `.html`
   (из scratchpad), с кратким итогом: что показывает пример, что проверено, что
   исправлено в компиляторе, открытые вопросы.

Пример считается готовым, только когда пользователь его принял. До этого — итерации
по замечаниям; каждое общее замечание — сразу в `standard.md`.
